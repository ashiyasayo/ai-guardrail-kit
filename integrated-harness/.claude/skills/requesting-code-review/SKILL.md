# 請求獨立程式碼審查

優先使用未參與實作、且不繼承實作對話歷史的 reviewer。只提供可核對的規格、diff、必要來源與測試證據，降低實作者自圓其說造成的盲點。`subagent-driven-development` 觸發的審查不得降級為實作者自審；若平台沒有子代理能力，停止並揭露無法完成獨立審查。單獨叫用本技能但平台不支援子代理時，可明確標示為較弱的 self-review，不得宣稱是獨立審查。

## 前置資料

主代理在審查前準備：

- 已核准的需求、驗收條件或輕量藍圖。
- 本次變更的 diff 與明確檔案範圍。
- 相關測試命令與結果。
- 已知限制，但不提供實作者對設計正確性的辯護或預設結論。

若沒有可辨識的規格，先向使用者確認會改變驗收結論的缺口；不要讓 reviewer 自行發明需求。

## Stage 1：Spec Compliance

啟動 fresh-context reviewer，只檢查：

- 每項需求與驗收條件是否有對應實作及證據。
- 是否遺漏必要行為、擴張範圍或改變公開契約。
- 測試是否真正涵蓋規格，而非僅驗證實作細節。

此階段不優先討論命名、格式或偏好。存在 blocking finding 時，不進入品質審查，先修復並重跑本階段。

## Stage 2：Code Quality

Stage 1 通過後，啟動另一個 fresh-context reviewer，檢查：

- 資安漏洞：SQL 注入、路徑走訪、未驗證的 RBAC／權限邊界與敏感資訊外洩。
- 非同步與併發：race condition、deadlock、未捕捉的 Promise／task 錯誤與資源生命週期。
- 防呆與回滾：資料庫 schema 變更的向下相容、失敗復原與降級備案。
- 測試覆蓋：新增邊界條件是否有足以防止回歸的單元或整合測試。

不得只憑摘要審查；reviewer 必須讀取範圍內的 diff 與必要來源。忽略純排版、命名與沒有正確性影響的個人偏好，不為了找碴製造裝飾性建議。

## 嚴重程度與工作流關卡

- `Critical`：會造成安全問題、資料損壞、核心需求失敗或不可接受的破壞性行為。阻塞完成，修復並通過重審前不得宣告完成。
- `Major`：高機率 bug、重要邊界漏失、公開契約不符或缺少關鍵回歸保護。阻塞完成，修復並通過重審前不得宣告完成。
- `Minor`：不影響目前正確性的局部可維護性或清晰度問題。記錄並在範圍內修正；不為純偏好啟動無限 review。

每項 finding 必須包含嚴重程度、檔案與位置、可重現或推導的證據、影響，以及可直接套用或容易核對的最小修正 diff。該 diff 是建議，不代表 reviewer 已獲准修改檔案。沒有證據的風格偏好不得列為 blocking。

## 修復與重審

1. 主代理先判讀 finding 是否有證據支持；錯誤 finding 應以具體證據駁回，不盲從。
2. 修復 Critical／Major 後，重跑相關測試與提出 finding 的階段。
3. 每階段最多兩輪；第二輪仍未通過時停止自動建立 reviewer，回報未解決問題並請使用者決定。
4. 最終交付列出兩階段結果、已修復 finding、仍保留的 Minor 與測試證據。

審查報告必須精簡條列。沒有 Critical／Major finding 時直接標示通過，只列真正影響風險的 Minor；不要用長篇摘要掩蓋結論。
