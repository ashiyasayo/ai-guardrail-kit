# 子代理驅動開發

以受控委派完成高風險工作的隔離驗證，並在完成點自動接上隔離的兩階段 code review。這是明確選用的高風險工作模式，不是一般多檔修改的預設流程。

## 適用閘門

常規任務由主代理直接完成，禁止為檢索、跑測試、平行嘗試或一般多模組修改派發子代理。只有同時符合下列條件才使用：

- 工作涉及三個以上外部依賴、核心金流、權限架構變更，或具有相當風險的資料庫遷移／跨模組重構。
- 至少有一個需要 fresh context 隔離驗證、且邊界清楚並可獨立驗收的工作單元。
- 平行工作不會修改同一檔案或責任範圍。
- 使用者、專案規範與平台允許委派。
- 委派節省的時間或專業分工價值，大於複製 context 與 review 的成本。

不因任務跨多檔就自動使用。少量工具呼叫可完成、需要共享大量隱性脈絡、或修改高度耦合時，留在主代理處理。資料庫遷移若只是機械性、可逆且規格完整，也不因此自動委派。

## 委派契約

每個實作子代理只取得完成該單元必要的最小 context：

- 明確目標、驗收條件與不在範圍內的事項。
- 擁有的檔案或模組；不得修改其他代理的責任範圍。
- 必要介面、測試命令、專案規範及已知風險。
- 提醒它不是唯一協作者，不得還原或覆寫他人變更。
- 明確禁止它再派發子代理或孫代理；它必須直接向主代理回報。

不要把整段對話歷史、其他任務細節或預期答案無差別傳給子代理。沒有獨立修改範圍的任務不得平行派發。

## 執行流程

1. 主代理先確認工作單元、責任邊界、依賴順序與整體驗收條件。
2. 派發可安全並行的實作任務；有依賴的任務依序執行。
3. 每個子代理回報修改檔案、測試證據、剩餘風險與可能衝突；其宣稱不等於驗收完成。
4. 主代理只核對整合所需的證據與工作樹狀態，不重做相同工作。
5. 在任務完成階段自動載入 `requesting-code-review`，以 fresh context 執行規格符合性與程式碼品質兩階段審查。
6. 修復 blocking findings 後，只重跑受影響的 review 階段與測試；不得無限建立新代理。

已通過上述高風險委派閘門後，若其中包含純檔案檢索或測試執行，使用平台實際提供的輕量、低成本模型。本段只是已獲准委派後的模型選擇規則，不構成新的委派理由。不要指定平台不存在的模型，也不要為符合範例名稱而降級到無法可靠完成任務的能力。只有工作需要高階推理且成本政策允許時，才使用較高成本模型。

## 成本與停止條件

- 同一工作單元只派一個實作代理；不以多代理競賽產生相同答案。
- 子代理不得派發任何下一層代理。
- 審查代理不得同時充當該變更的實作者。
- 每個 review 階段最多進行兩輪。第二輪仍有 blocking finding 時停止自動派發，整理證據並請使用者決定。
- 不因本技能建立 Git worktree；只有使用者明確要求或既有工作流確實需要隔離分支時才另行採用。
