# 估算與觀測吻合，不代表因果成立：單價高估兩倍導致次要成本被判為主因

日期：2026-08-03

一句話摘要：最佳化 `tests/codex_mode_switch_test.sh` 時，以「常見的 Python 啟動成本
× 估算呼叫次數」推得直譯器探測開銷約 1000–1300 秒，與實測 1138 秒高度吻合，
據此判定它是主因；移除後只降 302 秒（−27%），**剩下 836 秒仍未解釋**。
基數估對了，單價高估近兩倍。

## 坑

判斷流程看起來很嚴謹：

1. 讀原始碼，找到 `tests/helpers/fake-codex` 第 4 行的直譯器探測**每次呼叫都執行**，
   而 `add`／`remove`／`marketplace` 三個分支根本不用 Python。這是無爭議的浪費。
2. 數呼叫路徑：每次 `select-codex-mode` 約 5–7 次 `codex` 呼叫，測試約 60 次
   select／verify → 約 350–700 次探測用啟動。
3. 乘上「Windows 上 Python 啟動約 1.2–1.5 秒」→ 1000–1300 秒。
4. 實測值 1138 秒**落在區間內**。判定為主因，動手。

第 4 步是陷阱所在。吻合只證明模型與觀測不矛盾，不證明因果——一個高估單價、
低估其他成本的模型，也可能剛好加總到正確的總量。

實際結果：

| 測試 | 修改前 | 修改後 | 變化 |
| --- | --- | --- | --- |
| `codex_mode_switch_test.sh` | 1138s | 836s | −302s（−27%） |
| `codex_global_install_test.sh` | 62s | 48s | −14s |
| 全套回歸合計 | 約 1370s | 約 1058s | −23% |

（同一台機器、緊接前後兩次回歸，可直接比較。修改前另有 1167s、1257s 的同機歷史值。）

用實測反推：移除約 350–700 次啟動換得 302 秒，單次成本約 **0.4–0.9 秒**，
而非假設的 1.2–1.5 秒。結論從「主因」退化為「真實但次要」。

## 已排除與仍未解釋

**已排除：** `fake-codex` 現在完全不含 Python（`list` 分支改以純 bash 組 JSON，
格式逐字元對齊原先的 `json.dumps` 輸出）。探測開銷不再是候選。

**仍未解釋：836 秒。** 剩餘 Python 呼叫只在生產腳本裡（已由 grep 確認位置）：

- `scripts/codex-mode-lib.sh`：第 6-12 行的探測（每次 sourcing 一次）、
  第 41、115、202、231 行的實際呼叫
- `scripts/verify-codex-mode`：第 36、54 行（每次驗證兩次）

量級上與 836 秒相符——但**這又是同一種推論**，正是剛剛誤導過一次的那種。

## 下一步：先量測，不要再改

要繼續最佳化，下一步必須是取得硬數字（各腳本實際啟動幾次、單次多久），
而非依上面的推論直接動手。理由有兩層：

1. 方法上：這次已經證明「讀碼＋估算＋吻合」不足以定位主因。
2. 風險上：剩餘成本在**生產腳本**。這次的修改對象是測試輔助程式，改壞了只會讓
   測試變紅；改 `scripts/codex-mode-lib.sh` 會影響實際安裝流程，風險等級不同，
   更不該憑推論進行。

值得注意的是，即使定位錯了，這次的修改仍應保留——它移除的是無爭議的純浪費
（不需要 Python 的分支付出探測代價），與主因是誰無關。

## 可重用原則

- **效能判斷的驗收是修改後的實測差值，不是估算與觀測的吻合度。**
- 估算由「基數 × 單價」構成時，兩者要分別檢驗。基數可由讀碼精確得出，
  單價幾乎總是借用經驗值——後者是誤差的主要來源，也最容易被吻合的總量掩蓋。
- 先做零風險、無爭議的那一半，用它的實測成效校準單價，再決定要不要碰高風險部分。
  這次因此只花了一次測試回歸就把單價修正到正確量級。
