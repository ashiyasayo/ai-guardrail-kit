# 輕量化需求釐清與架構設計

在寫程式碼前釐清真正影響實作方向的需求，產出足以執行、但不重複實作內容的輕量藍圖。

## 路由條件

- 需求有多義性、會改變資料庫 schema 或公開 API 契約，或重構跨越三個以上模組時使用。
- 單一檔案修改、明確的 bug 修復、設定調整，或使用者已提供精確實作規格時直接實作。
- 不採用「只要有極小可能適用就強制載入」的規則；依實際複雜度與決策風險判斷。

## 1. 上下文探勘與蘇格拉底式釐清

1. 先讀取相關既有檔案、介面、測試與專案決策；不要詢問從專案即可查得的事實。
2. 只詢問會實質改變結果的邊界條件、錯誤策略或架構取捨。
3. 每次最多提出一至兩個最關鍵問題；優先給二至三個互斥選項，將推薦選項放在第一個並說明影響。
4. 資訊已足夠時直接進入方案權衡，不為了流程強行提問。

## 2. 方案權衡

提出二至三個本質不同且可行的方案；若只有一個合理方案，簡短說明原因，不製造陪榜方案。每個方案只需包含：

- 名稱與核心思路。
- 維護成本、效能及相容性的主要優缺點。
- 推薦方案及其理由。

等待使用者確認的前提是：不同選擇會導致實質不同結果。若使用者已授權依推薦方案執行，可直接繼續。

## 3. 反雙重實作藍圖

方案確認後，在對話中提供極簡藍圖：

- 列出目標檔案路徑。
- 列出預計新增或修改的函式／介面簽章。
- 以不超過十行的虛擬碼描述核心邏輯。
- 列出最接近變更且足以證明行為的驗證方式。

藍圖不得包含可直接貼入專案的完整實作程式碼。真正的程式碼只在執行階段撰寫一次。

除非使用者明確要求保存設計文件，否則不要建立 `PLAN.md`、`SPEC.md`、`docs/plans/` 或其他中間文件。專案既有的強制計畫閘門不屬於此禁令，仍應用最精簡內容滿足其契約。

不得因本技能自動建立 Git worktree、切換分支或派發子代理。只有工作具一定規模、可真正獨立並行，且專案與平台規則允許時，才另行考慮委派。

使用者沒有異議或已授權直接執行時，在目前 context 中依藍圖修改並測試。
