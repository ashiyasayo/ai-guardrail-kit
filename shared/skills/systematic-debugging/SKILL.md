# 系統化根因除錯

## 核心鐵律

未定位並以證據驗證根本原因前，不提交猜測性修復。不得為了讓測試通過而刪除斷言、放寬型別檢查，或加入吞掉錯誤的無意義例外處理。

## Phase 1：根因調查

1. 完整閱讀 stack trace、log、錯誤碼與相關警告。
2. 找出穩定、最小的重現步驟；合適時先加入會失敗的最小測試。
3. 用 `git diff` 與近期歷史確認是否與現有未提交修改或近期變更相關；保留使用者既有工作。
4. 系統跨多層時，在每個信任或資料邊界檢查輸入與輸出，定位第一個狀態偏離預期的節點。

## Phase 2：模式比對

1. 找出專案內功能相近且正常運作的實作。
2. 比對正常與故障路徑在環境變數、依賴注入、非同步處理、生命週期、權限與資料形狀上的差異。
3. 只保留有觀察證據支持、且能解釋症狀的差異。

## Phase 3：單一假設驗證

1. 用一句話陳述：「問題位於 X，因為觀察到 Y。」
2. 以最小修改、精準診斷 log 或聚焦測試驗證假設。
3. 一次只改一個變數。假設失敗時，移除本次實驗性變更，再提出下一個假設。
4. 不使用會覆寫使用者工作的 `git checkout`、`git reset` 或同類命令還原；只精準撤回自己剛加入的實驗內容。

## Phase 4：修復與回歸保護

1. 修復已確認的根因，不在下游遮蔽症狀。
2. 加入能在修復前失敗、修復後通過的單元或整合測試；若無法新增，說明限制及替代證據。
3. 執行最接近變更的測試，再依影響面執行合理的回歸測試。
4. 回報根因、修復、驗證證據與未驗證風險。

## 三次停損

若連續三個修復假設均被證偽：

- 立即停止修改，不再追加猜測性修補。
- 整理已排除的三個方向、各自證據及觀察到的矛盾。
- 重新檢查架構或執行環境前提；缺少關鍵資訊時，向使用者提出一至兩個具體問題。

本技能不要求建立 Git worktree，也不要求派發子代理。除錯應優先保留同一 context 中已累積的證據；只有可獨立調查的邊界確實能並行，且委派效益大於脈絡複製成本時才考慮子代理。
